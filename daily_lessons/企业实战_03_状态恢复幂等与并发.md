## 1. 重启恢复的对象是什么

Day 24 把审批暂停点保存在图的检查点里。本项目的业务暂停点是数据库中的 `pending_review`。任何实例收到审批请求，都能根据工单 ID 找到待审批数据并继续执行。后续接入 LangGraph 时，图的检查点负责恢复模型消息和节点进度，工单表负责记录最终业务状态。应为同一次审批保存稳定的业务 ID，并使业务写入可安全重放。 [LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

## 2. 创建工单如何处理网络重试

1. 用户每次发起新操作时生成新的 `Idempotency-Key`。遇到超时，原操作的重试继续使用原键。
2. 数据库尝试插入。冲突目标为 `(tenant_id, owner_id, idempotency_key)`。
3. 插入成功，写入 `created` 事件并提交。如果唯一键已存在，读取原记录并比较规范化后的问题。
4. 参数相同返回原工单的当前快照。参数不同返回 409，调用者应检查是否误用了旧键。

| 方法 | 输入和返回 | 类似方法和选用条件 |
| --- | --- | --- |
| `conflict_insert(session, Ticket)` | 读取连接方言，返回 SQLite 或 PostgreSQL 的 Insert 对象。 | 通用 `sqlalchemy.insert()` 可执行普通 INSERT。需要 `ON CONFLICT` 时使用相应方言的 Insert。 |
| `.on_conflict_do_nothing(index_elements=[...])` | 为指定唯一约束冲突生成跳过写入的 SQL。后续由业务比较请求内容。 | `.on_conflict_do_update(..., set_=...)` 适合新版本覆盖旧记录，例如知识库导入。 |
| `.returning(Ticket.id)` | 让数据库返回本次写入的 ID。没有插入或更新时，结果没有行。 | `flush()` 后读取 ORM 对象主键适合普通 ORM 插入。`rowcount` 适合只需判断影响行数并已确认驱动支持的场景。 |
| `.scalar_one_or_none()` | 从执行结果取唯一一行的第一列，零行返回 `None`。 | `.scalar_one()` 要求存在一行。`.scalars().all()` 适合批量返回多个 ID。 |

对于多字段请求，可以先定义规范化规则，再存一个请求指纹。幂等键的有效期、旧结果保留多久、是否重放原响应，都需要写进接口契约。

## 3. 两个审批请求同时到达时

核心是 `UPDATE tickets ... WHERE id = ... AND tenant_id = ... AND status = 'pending_review'`。检查与变更由数据库执行在同一条语句里。第一个成功提交的操作留下审批状态及审计。第二个操作看到工单已到终态。若操作人和决定完全相同，视为重试。其余情况返回 409。

| 并发方法 | 适用情形 |
| --- | --- |
| 带条件的 `UPDATE ... WHERE` | 单张表的状态前置条件可以写在 WHERE 中，本课用这一种。 |
| `SELECT ... FOR UPDATE` | 在 PostgreSQL 事务中锁定选中的记录，适合多个判断与写入必须串行完成的流程。要控制锁持有时间。 |
| 乐观锁版本号 | 使用 `WHERE version = expected_version`，适合用户打开编辑页后过一段时间再提交的场景。 |
| Python `threading.Lock` | 适合保护单个进程里的内存结构。多个服务进程各自持有锁，数据库一致性仍由数据库机制提供。 |

## 4. 失败回滚和外部副作用

`with session.begin()` 将工单与审计作为一个事务提交。测试故意让审计写入抛异常，然后用原幂等键再次发起请求。第二次收到 201，说明第一次工单也已回滚。

接入外部退款 API 时，可以学习 **事务 Outbox**。业务事务提交工单状态和待发事件，后台 worker 读取并重试，外部系统用同一个业务幂等键去重。外部已经扣款、响应却超时时，需要查询外部状态或对账；数据库回滚只能回滚本库数据。项目当前审批仅操作本库，供你先练透事务边界。
