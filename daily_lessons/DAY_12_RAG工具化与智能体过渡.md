## 💡 静态 RAG 与 Agent 工具化 RAG 的本质区别

| 对比维度 | DAY 09 & DAY 11（静态 RAG 检索） | DAY 12（Agent 工具化 RAG） |
| :--- | :--- | :--- |
| **执行机制** | **硬编码**：不管用户问啥，代码第一行直接调 `collection.query()` | **模型自主意图判断**：由大模型思考“这个问题需不需要查知识库” |
| **闲聊与日常问题** | 依然傻傻地去检索数据库，白白浪费检索算力并容易误伤相关度 | 直接礼貌作答，**完全不触发检索**，极度敏捷 |
| **复合复杂问题** | 只能查一次知识库并直接作答 | 可以在 Agent 的决策循环中，作为工具箱里的**其中一把武器**按需调度 |

## 🛠️ 怎么把一个 RAG 函数变成一个标准 Tool？

核心只需要三步（这正是下一课 DAY 13 的核心基石）：

1. **写出底层的业务执行函数**（如 `search_company_policy_tool`，接收 `query`，返回查出来的文字）；
2. **用 Pydantic 定义一份 JSON Schema**（告诉大模型这个工具叫什么名字、在什么场景下应该使用它、需要传什么参数）；
3. **在调用大模型时传入 `tools=[KNOWLEDGE_TOOL_SPEC]`**：
   - 如果大模型返回 `tool_calls`，我们就去执行本地函数并回传结果；
   - 如果没有，就直接输出回复。
